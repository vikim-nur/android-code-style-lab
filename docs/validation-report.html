Что мы проверили — простыми словами

Мы проверяли три вещи: сможет ли плагин доставить одинаковые настройки, безопасно ли работает форматирование перед коммитом и совпадает ли результат разных способов запуска.

Профили готовы для обсуждения с командой. Проверки ниже выполнялись в отдельных тестовых папках. Настоящие приложения и их Git-хуки мы не меняли.

Что пока не подтверждено: новый JAR через настоящий шорткат Studio. Автоматическая попытка остановилась по тайм-ауту. Работа движка IDE подтверждена отдельно, но её недостаточно, чтобы обещать поведение шортката. Реальный сервер CI и пилот приложения ещё не запускались.

12 проверок плагина Gradle

Gradle-плагин — это наша упаковка настроек и команд. Проверяли, что он приносит нужные файлы, обновляет их и не затирает правки разработчика.

  1. Первое подключение

    Создали пустой тестовый проект и подключили плагин. Он сам положил конфиг, JAR правил и настройку для IDE. Вручную эти файлы не копировали.

  2. Обычная сборка

    Запустили assemble: форматирование и анализ не запускались, исходный файл не изменился. Это маленький тестовый проект, не замер Android-сборки.

  3. Проверка видит неправильное оформление

    В файле была цепочка Modifier в строку. Проверка сообщила о нарушении и завершилась с отказом. Сам файл не исправляла.

  4. Исправление работает

    Запустили форматирование: Modifier перенёсся по строкам, пробелы у типов исправились.

  5. Второй запуск не меняет уже исправленное

    Сразу запустили форматирование ещё раз. Файл остался побайтно тем же.

  6. Detekt действительно запускается

    В учебном коде оставили число, нарушающее правило MagicNumber. Detekt нашёл его. Это техническая проверка запуска; набор правил Detekt для команды ещё не выбран.

  7. Общая проверка проходит на допустимом примере

    Убрали контрольное нарушение и запустили qualityCheck — форматирование и техническая проверка Detekt прошли.

  8. Повторная проверка использует предыдущий результат

    Снова запустили qualityCheck без изменений. Обе проверки получили UP-TO-DATE: заново тот же код не анализировали.

  9. Новая версия приносит новые настройки

    В контрольной копии поменяли версию плагина и порог переноса Modifier. После подключения обновились конфиг и путь к JAR. Вручную внутри IDE новый файл не выбирали; его фактическое применение шорткатом здесь не проверялось.

  10. Свои изменения разработчика не затираются

    Вручную поменяли управляемый конфиг и запустили плагин. Он остановился с сообщением о конфликте. Остальные управляемые файлы не переписал.

  11. Удалённая настройка восстанавливается

    Удалили тестовый файл настройки IDE. Следующий запуск восстановил его.

  12. Пересохранение XML самой Studio не считается конфликтом

    Имитировали изменение отступов XML и отсутствие настройки с её стандартным значением. Плагин принял равнозначную запись и не стал её переписывать.

16 проверок Git-хука

Хук — программа, которую Git вызывает перед коммитом. В отдельном тестовом репозитории действительно выполняли команды commit. В одних случаях коммит должен был пройти, в других — остановиться. Все 16 проверок дали ожидаемый результат.

Проверенный порядок: хук исправляет оформление → останавливает коммит → разработчик смотрит diff → добавляет исправления → повторяет коммит. Сам хук ничего не добавляет в индекс и не прячет изменения.

  1. Код добавлен в коммит и требует форматирования

    Хук исправил рабочий файл и остановил коммит, чтобы разработчик посмотрел diff. Содержимое будущего коммита не менял.

  2. Повторный коммит без добавления исправлений

    Исправления ещё не добавлены в индекс. Хук остановился и не стал форматировать файл повторно.

  3. Исправления посмотрели и добавили

    Повторный коммит прошёл, файл не изменился.

  4. В коммит добавлена только часть файла

    В том же файле есть другие, ещё не добавленные изменения. Хук остановился до записи: обе версии сохранились.

  5. Меняется только документация

    Коммит прошёл без запуска форматтера. Посторонний изменённый Kotlin-файл не тронут.

  6. Несколько файлов, в имени есть пробелы

    Оба файла обработались правильно. После исправления хук остановил коммит для просмотра.

  7. Повтор после добавления этих исправлений

    Коммит нескольких файлов прошёл, новых исправлений не было.

  8. Файл переименован

    Переименованный Kotlin-файл проверен, коммит прошёл.

  9. Kotlin-файл удалён

    Хук не пытался открыть отсутствующий файл; коммит прошёл.

  10. В коде синтаксическая ошибка

    Коммит остановлен. Рабочий файл и добавленная в индекс версия остались без изменений.

  11. Меняется Kotlin-скрипт .kts

    Форматирование исправило .kts; коммит остановлен для просмотра.

  12. Исправленный .kts добавили снова

    Коммит прошёл, новых исправлений нет.

  13. Форматтер недоступен

    Коммит остановлен с ошибкой; файлы не менялись.

  14. Форматтер снова доступен

    Тот же коммит прошёл.

  15. Сразу шесть учебных файлов

    Все шесть отформатировались за один вызов движка. Содержимое индекса осталось прежним.

  16. Исправления во всех шести файлах добавили

    Коммит прошёл; рабочая папка тестового репозитория чистая.

Что значит «44 совпадения»

Взяли 22 учебных файла и два профиля. Для каждого сочетания получили текст через командную строку и через движок плагина IDE. Сравнили результаты: 22 × 2 = 44 пары, во всех текст одинаковый.

Это не 44 правила и не проверка всего Android Studio. Сам шорткат может сначала запустить встроенное форматирование Studio — этот полный путь ещё нужно подтвердить.

Что значит повторное форматирование

Отформатировали файл, затем сразу отформатировали его ещё раз. Второй запуск не должен снова переставлять код. В проверенных примерах результат не менялся: правила не «тянут» оформление туда-сюда.

Что проверили с кэшем

Кэш — сохранённая работа предыдущего запуска. Проверили четыре ситуации:

  1. Ничего не меняли — Gradle использовал сохранённый план запуска.
  2. Изменили код — проверка действительно запустилась, нашла нарушение и не стала исправлять файл.
  3. Вернули допустимый код — проверка прошла.
  4. Удалили настройку IDE — Gradle пересобрал план, а плагин восстановил файл.

Сохранённый план запуска и пропуск самой проверки — разные вещи. Gradle может использовать прежний план и при этом заново проверить изменённый файл. Повторный запуск быстрее, но не бесплатный.

Сколько ждать разработчику

  • Первый наблюдаемый вызов хука с форматтером: около 2,5 с.
  • Следующие вызовы с форматтером: обычно 0,7–0,8 с.
  • Когда форматтер не запускался: около 0,1 с.
  • Повторная Gradle-проверка без изменений: около 0,6 с.

Это наблюдения на этой машине с уже загруженными зависимостями и маленьким тестовым проектом. Скорость всех Android-проектов по ним предсказывать нельзя.

Что получилось на 567 файлах эталона

На копиях исходников профиль по эталону изменил 444 файла помимо перевода строки в конце, стандартный профиль — 548. В обоих повторный запуск стабилен. Остались 4 замечания о длине строки у первого и 11 у второго: некоторые длинные строки форматтер сам не разделяет. Их нужно разобрать вручную. Сам эталон неоднороден, поэтому это предложение общего стиля, а не точная копия каждого файла.
