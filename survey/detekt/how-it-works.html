К вопросу

Запрет wildcard-импортов

Это касается импортов в остальных проверяемых Kotlin-файлах, а не только показанного пакета. Настройки автоматического добавления импортов в Android Studio должны соответствовать выбранной политике, иначе IDE и проверка будут спорить.

Рекомендуемый владелец — ktlint 1.8.0: ktlint_standard_no-wildcard-imports = enabled. ij_kotlin_packages_to_use_import_on_demand задаёт разрешённые пакеты; unset убирает их. Правило не разворачивает * автоматически, импорты нужно исправить в Android Studio. Старые примеры проверялись Detekt 1.23.8, где excludeImports штатно разрешает java.util.*; это не принятие того исключения командой. Не дублировать проверку в Detekt.

ij_kotlin_packages_to_use_import_on_demand: Разрешать ли пакеты-исключения для import ….*?; штатно unset

Не разрешать пакеты-исключения: unset

Разрешить java.util.*; остальные wildcard-импорты запретить: java.util.*

Нужно решение команды о политике. На искусственных файлах ktlint1.8 проверены явные импорты, запрет * и whitelist; рабочий общий профиль и настройки Android Studio ещё не проверены.

Порядок параметров Composable

Это порядок объявления, не переносы строк. Перестановка затронет другие Composable и может сломать позиционные вызовы. Правило порядка само не решает, является последняя лямбда событием или UI-контентом — для этого есть отдельный вопрос.

Готовое правило ComposableParamOrder из Compose Rules 0.4.23. Порядок задан реализацией; типы modifier и лямбд могут распознаваться с учётом настроек библиотеки. Перед изменением публичного API нужен отдельный разбор вызовов.

Нужен выбор области нового соглашения и согласование публичных API; полезность во всех проектах пока не проверена.

Обязательный event-callback не последним

Проверка не запрещает все последние callback. В этой версии она проверяет компоненты, которые создают UI и имеют modifier: последний параметр — обычная лямбда с именем on..., без значения по умолчанию и без @Composable.

Готовое правило LambdaParameterEventTrailing из Compose Rules 0.4.23. Распознавание UI-компонентов и modifier зависит от настроек библиотеки. Перестановку параметров существующего API не выполнять автоматически.

Команда выбирает новое соглашение для API, а не считает текущие 8 мест багами.

Callback-имена в настоящем времени

Правило не требует назвать каждый параметр с on и не проверяет все имена приложения. Оно рассматривает подходящие параметры-лямбды Composable; переименование может затронуть вызовы с именованными аргументами.

allowedLambdaParameterNames: Дополнительные имена callback, которые можно оставить; штатно []

Параметр Modifier у UI-компонентов

Правило не требует modifier у каждой функции с @Composable. Учитываются видимость и создание UI; Preview, override, методы интерфейсов и ряд других случаев пропускаются. Наличие параметра ещё не доказывает его правильное применение внутри компонента.

checkModifiersForVisibility: only_public (штатно), public_and_internal или all; modifierMissingIgnoreAnnotated — исключения по аннотациям. Списки UI-emitter/overlay влияют на распознавание компонентов. Исключения для корневых экранов и overlay нужно согласовать.

checkModifiersForVisibility: У каких UI-компонентов требовать параметр Modifier?; штатно only_public

Только у публичных компонентов (public): only_public

У публичных и доступных внутри модуля (public + internal): public_and_internal

У всех подходящих компонентов, включая private: all

modifierMissingIgnoreAnnotated: Исключения по аннотациям общего правила; штатно []

Без дополнительных исключений по аннотациям: []

ignoreAnnotated: Дополнительные исключения по аннотациям Detekt-адаптера; штатно []

Без дополнительных исключений по аннотациям: []

Выбор команды нужен для области нового API-соглашения; перед проверкой размечать 48 случаев Saima и проектные wrapper.
