Compose API

Пять независимых соглашений: порядок, trailing event, имена callback, имена Preview и наличие Modifier. Порядок сам не отличает event от content; private Preview — отдельное действующее требование. Движок не различает старые и новые API: готового new-only режима нет.

Порядок параметров Composable

Compose.ComposableParamOrder

Параметры Composable предлагается располагать так: обязательные, затем modifier, затем параметры со значением по умолчанию; последняя лямбда может оставаться в конце.

Основания и ограничения

Для новых API рекомендовать обязательные параметры → modifier → параметры с default → необязательная trailing-функция. Существующие позиционные контракты не переставлять массово.

Оставить выбор соглашения для новых API. Семантический контроль показывает, что правило допускает required event последним; event/content регулируются отдельным правилом. Возраст API движок не определяет, автоматического new-only scope нет.

Это порядок объявления, не переносы строк. Перестановка затронет другие Composable и может сломать позиционные вызовы. Правило порядка само не решает, является последняя лямбда событием или UI-контентом — для этого есть отдельный вопрос.

Перестановка параметров меняет позиционные вызовы; правило порядка не определяет семантику event/content.

Обязательный event-callback не последним

Compose.LambdaParameterEventTrailing

Обязательный обработчик вроде onClick предлагается не ставить последним параметром UI-компонента. Последнюю лямбду оставляем для content, чтобы запись Component { ... } не выглядела как UI-контент, когда это событие.

Основания и ограничения

Рекомендовать обязательный event-callback перед modifier для новых UI API; не менять действующие контракты автоматически.

Проверенные исключения: default callback, отсутствие modifier, отсутствие emission, Composable-lambda и имя не on... не дают того же finding. Новое соглашение не объявлять общим запретом trailing callbacks. Позиционную миграцию не считать безопасной.

Проверка не запрещает все последние callback. В этой версии она проверяет компоненты, которые создают UI и имеют modifier: последний параметр — обычная лямбда с именем on..., без значения по умолчанию и без @Composable.

Существующие вызовы API могут использовать trailing event; изменение требует совместимости.

Callback-имена в настоящем времени

Compose.ParameterNaming

Для callback с именем on... предлагается настоящее время: например, onClick вместо onClicked и onTextChange вместо onTextChanged.

Основания и ограничения

Рекомендовать onClick/onTextChange для новых callback; существующие onClicked/onTextChanged не переименовывать массово.

Сохранить стилевую развилку, не defect gate. Проверены present/past, built-in onFocusChanged, allowlist, non-lambda и другой префикс. Переименование затрагивает named calls, новые API сам детектор не распознаёт.

Правило не требует назвать каждый параметр с on и не проверяет все имена приложения. Оно рассматривает подходящие параметры-лямбды Composable; переименование может затронуть вызовы с именованными аргументами.

Переименование затрагивает named args и публичные SDK; эвристика прошедшего времени не универсальна.

Основания и ограничения

Параметр Modifier у UI-компонентов

Compose.ModifierMissing

Подходящим UI-компонентам предлагается добавить параметр Modifier, чтобы вызывающий код мог задавать размер, отступы и другие свойства снаружи.

Основания и ограничения

Рекомендовать modifier у публичных переиспользуемых layout-компонентов; корневые screens и overlay рассматривать отдельно. Сначала отчёт и API-review.

Область должна быть явной: RootScreen не пропускается по имени; проверены private/all, Preview, return value, interface/override, unknown wrapper, overlay и annotation-ignore. Отсутствие finding у неизвестного wrapper не доказывает правильность API.

Правило не требует modifier у каждой функции с @Composable. Учитываются видимость и создание UI; Preview, override, методы интерфейсов и ряд других случаев пропускаются. Наличие параметра ещё не доказывает его правильное применение внутри компонента.

Bottom sheet может не иметь смысла модифицировать как layout-узел. Нельзя переносить список Nur-компонентов во все проекты без сверки.
