# Анкета А/Б по форматированию

Анкета для согласования: 21 вопрос по различиям из 45 тем каталога. Вариант А повторяет рассматриваемую форму конкретного образца «Мой О!», вариант Б показывает наше предложение. Имена и логика в публичных примерах упрощены; корпоративные исходные фрагменты хранятся отдельно в локальном анализе. В самом эталоне встречаются разные формы одного объявления.

Откройте [анкету](https://vikim-nur.github.io/android-code-style-lab/survey/reference-ab/). `technical.html` содержит проверку вариантов, `coverage.html` — охват тем. В `results.html` есть явно подписанная демонстрация на вымышленных участниках. Настоящих голосов в ней нет.

## Именные ответы и итоги

Участник выбирает А/Б, указывает имя и нажимает «Открыть ответ в GitHub». Затем сам отправляет подготовленное Issue из своего GitHub-аккаунта. Подключать GitHub к Codex или передавать токен не требуется. Ответы и имена в публичном репозитории будут публичными.

Страница результатов по кнопке читает публичные Issues через [REST API](https://docs.github.com/en/rest/issues/issues). GitHub поддерживает [чтение API из браузера через CORS](https://docs.github.com/en/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests). Собственного сервера, автоматических коммитов и GitHub Actions для подсчёта нет.

Учитывается последняя анкета каждого аккаунта по номеру Issue; стабильный GitHub user ID не даёт посчитать переименованный аккаунт дважды. Если последний ответ некорректен, старый вместо него не подставляется. Пропуски не голосуют ни за А, ни за Б; ничья показывается отдельно. Другая версия анкеты, боты и Pull Requests не учитываются. Закрытие Issue не отменяет ответ. Для изменения нужно отредактировать свою анкету или отправить новую.

Итоги показывают число голосов и лидирующий вариант по каждому вопросу, а также имена, аккаунты и индивидуальные ответы. Можно скачать читаемый Markdown-итог для GitHub и JSON с данными. Выгрузка не публикуется автоматически. Опрос открыт: организатор сверяет участников с командой перед подведением итогов.

Код и содержание вопросов закреплены идентификатором версии. После начала голосования содержимое вариантов менять под прежней версией нельзя. `questions.json` и `data.js` должны обновляться вместе генератором.

## Реализуемость

Для Б проверен локальный JAR 0.3.2-candidate.1, кроме порога только для data class: он использует прототип. Варианты А проверены как на текущем JAR, так и на отдельном прототипе; точная доступность показана в technical.html. Для вариантов, требующих дополнительного кода, создан отдельный экспериментальный ruleset, который не установлен в Studio или приложения. На конкретных примерах обе стороны преобразуются из противоположного оформления, стабильно форматируются повторно и проходят check.

Проверены все 16 сочетаний четырёх решений по наследованию. Все стабильны и проходят check; 10 дают именно независимо выбранные картинки, в 6 есть перекрёстное влияние общих настроек. Поэтому голоса не превращаются автоматически в готовую конфигурацию: сначала нужно согласовать общий принцип, проверить итоговый пакет и утвердить его с лидами. Все сочетания 21 решения не проверялись.

Для отдельных решений остаётся цена поддержки: своё форматирование наследования и аннотаций, порядок выполнения правил, отключение пересекающихся стандартных проверок и повторная проверка при обновлении ktlint/IDE. Общий предел строки во всех конфигах анкеты — 140. Вопрос с искусственным лимитом 200 удалён. Порог data class отделён от обычных классов через nur_data_constructor_min_parameters; при значении 3 три и более параметра располагаются столбиком. Перенос аргументов базового класса влияет также на холдеры. Подробности находятся рядом с вопросами и в техническом отчёте.

Проверка логики голосования из корня репозитория:

```sh
node --test scripts/test_ballot.cjs
```

Исходники экспериментального ruleset, JAR и локальные отчёты не входят в эту публикацию анкеты. Проверенные результаты описаны в `technical.html` и `verification.json`; готовой конфигурацией для установки в приложения это не является.

В этой работе реальных Issue с голосами не создавали до публикации сайта. Проверки формы используют подставленные ответы API; настоящий внешний прогон — после отдельной команды публикации. Проверка DOM выполнена, визуальная проверка в браузере осталась ограничением окружения: Chrome headless завершился с SIGABRT.
