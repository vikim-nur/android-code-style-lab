Можно ли выбранный вид сделать автоматическим?

Б — результат локального JAR 0.3.2-candidate.1, кроме вопроса о data class: для ограничения только data class используется отдельный прототип. А — форма из выбранного эталонного образца; имена в примерах заменены. Во всех действующих конфигах анкеты max_line_length = 140; отдельного выбора 200 нет. Для А отдельно проверен экспериментальный JAR 0.4.0-ballot.1. Он не установлен в Studio и не внедрён в приложения.

Проверка «строго работает» означает: исходный вариант форматируется точно как показано, повтор не меняет результат, check проходит и противоположный вариант тоже преобразуется в выбранный. Это проверка конкретных примеров, не гарантия любого Kotlin-кода.

Отключить правило и сохранить вручную сделанный перенос — недостаточно: если из другого оформления нужный вид не получается, такой вариант не помечается готовым.

Некоторые настройки влияют на несколько вопросов. Выбранное командой сочетание надо проверить целиком до утверждения; результат опроса сам настройки не меняет.

Проверка сочетаний наследования

Проверены все 16 сочетаний четырёх вопросов: аргументы ViewModel, callback адаптера, короткий базовый тип и несколько базовых типов. Все сочетания стабильны и проходят check. В 6 из 16 часть примеров получает другой вид из-за общих настроек. Это связь правил, а не падение форматтера.

Например, раскрытие аргументов любого базового типа, перенесённого ниже объявления, также раскрывает binding.root у короткого холдера и view у холдера с интерфейсом. Перед утверждением победившего сочетания нужно решить, должно ли правило быть общим или условие следует разделить. Весь набор из 21 решения пока не утверждён и не проверен во всех сочетаниях.

Как хранятся голоса

Участник отправляет свою анкету как GitHub Issue из своего аккаунта. Страница результатов читает публичный API без токена. Имя берётся из анкеты, аккаунт — из автора Issue. Учитывается последняя анкета аккаунта, пропуски не считаются голосами. Сводка показывается на странице результатов.

Голоса другой версии анкеты, некорректные ответы, боты и Pull Requests не учитываются. Реальная отправка на GitHub в этой проверке не выполнялась.

Граница проверки длинных параметров

Проверены 19 случаев: data class и обычный класс с 1–4 параметрами из двух исходных раскладок, длинные параметры и длинное условие. Итоговое форматирование стабильно и check проходит. В двух опытах с одним очень длинным параметром первый вызов format также сообщил max-line-length, хотя своё позднее правило уже перенесло строку; повтор и отдельный check чистые. Этот порядок диагностики ещё требует доработки перед внедрением.
