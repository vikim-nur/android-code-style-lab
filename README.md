## Что предлагаем

| | А — по эталону | Б — штатный ktlint |
|---|---|---|
| Основа | `android_studio` + наши правила | `ktlint_official` |
| Длина строки | 140 | 120, выбрано явно |
| Дополнительные правила | 6 включены из 8 в JAR | Весь набор nur отключён |
| Конфиг | [nur-reference.editorconfig](config/profiles/nur-reference.editorconfig) | [ktlint-official.editorconfig](config/profiles/ktlint-official.editorconfig) |

А собран по разобранным шаблонам эталонного кода. В местах с разным оформлением сделан явный выбор: это кандидат на единый стиль, а не утверждение, что все исходники уже выглядели одинаково. Б — готовая альтернатива поддерживаемого движка, не универсальная best practice и не точная копия Google Style.

На странице сравнения показаны только различающиеся результаты на одинаковом учебном входе. Есть оформление Modifier, функций, конструкторов, адаптеров, наследования, when и лямбд. Все публичные примеры синтетические; исходников приложений здесь нет.

[Контракт по всем 23 областям оформления](docs/reference-coverage.md) различает автоисправление, допустимые варианты и ограничения. Некоторые уже многострочные конструкции сохраняются; полного схлопывания любого Kotlin-ввода в единственный вид не обещаем.

## Что делать коллеге

1. Открыть анкету команды: в каждом вопросе два варианта кода и простое объяснение выбора. В вопросе наследования — показанный образец и возможность предложить конкретное изменение.
2. Выбрать настройки по отдельности: запятые, переносы, параметры, when, intent, Modifier. Пометка по эталону — ориентир, ответ за участника не выбран.
3. Скачать ответы обычным текстом и передать организатору обсуждения. JSON нужен только для продолжения позже; GitHub — дополнительный вариант ручной отправки.

Ответы не предвыбраны. Форма ничего не отправляет автоматически. Issue станет публичным после отправки на GitHub; Текст и JSON можно скачать без аккаунта. Несохранённый ответ теряется при закрытии страницы.

После выбора проверим сочетание настроек, согласуем с лидами и проведём отдельный пилот. Голосование и техническая проверка сами по себе не означают внедрение.

## Как устроен комплект

JAR расширяет **ktlint 1.8.0**. Настройки лежат в `.editorconfig`; наши правила добавляют нужное поведение поверх штатного движка. [Описание и ограничения](docs/candidates.md), [исходники правил](tooling/nur-ktlint-rules/src/main/kotlin/kg/nur/quality).

Транспортный прототип Gradle `kg.nur.quality` упаковывает JAR и профиль А из единственного `config/profiles/nur-reference.editorconfig`. Версия задаётся в `tooling/nur-quality-plugin/src/main/resources/quality/versions.properties`. При применении plugin синхронизируются управляемый конфиг и проектный путь JAR для IDE. Локальные неуправляемые правки вызывают конфликт, а не затираются. Б пока подключается отдельным конфигом; переключатель профилей в plugin не реализован.

После подключения прототипа доступны:

```sh
./gradlew qualitySync         # восстановить настройки; sync также идёт при применении plugin
./gradlew qualityFormat       # исправить форматирование
./gradlew qualityFormatCheck  # проверить без исправлений, команда для CI
```

Небольшой тестовый `assemble` не запускал форматирование/анализ и не менял исходник. Накладные расходы конфигурации plugin в Android-сборке отдельно не измерены. Прототип Git-хука тестировался отдельно и в приложения не устанавливался; путь доставки всей команде ещё предстоит проверить пилотом.

## Сборка и повтор проверки

JDK 21 для сборки, bytecode Java 17; Gradle wrapper 9.4.1.

```sh
./gradlew :ktlint-rules:jar
./gradlew -p tooling/nur-quality-plugin build
python3 scripts/verify_profiles.py --cli /path/to/ktlint-1.8.0-all.jar --rules artifacts/nur-style-rules-0.2.0-candidate.1.jar --output /path/to/owned-result
```

Скрипт работает на копиях учебных файлов; не указывайте рабочую папку приложения как output. [Контрольные суммы JAR, исходников и профилей](artifacts/manifest.json).
