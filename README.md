# Android Code Style Lab

Обсуждаем общий стиль Kotlin для Android: смотрим на код, выбираем правила, проверяем их инструментами. **Это предложение для команды, не утверждённый стандарт.** Сейчас занимаемся форматированием; статический анализ обсудим отдельно.

**[Открыть анкету в браузере](https://vikim-nur.github.io/android-code-style-lab/survey/)** · [Подробные соглашения](docs/formatting.md) · [Наши пять правил](docs/custom-rules.md) · [Пример целого файла](examples/after/Example.kt)

## С чего начать коллеге

1. Посмотрите предлагаемый стиль ниже и целый файл в анкете.
2. Выберите варианты в девяти вопросах. По умолчанию ответы не отмечены; можно ответить только на часть вопросов.
3. Добавьте комментарий, если нужно исключение или другой вариант.
4. Скачайте JSON с ответами, чтобы продолжить позже или передать результат. Либо откройте подготовленный черновик GitHub Issue кнопкой в форме и опубликуйте его вручную.

Форма ничего не отправляет автоматически. Ответ в GitHub Issue станет публичным только после вашей отправки на GitHub. Для этого нужен GitHub-аккаунт; скачивание JSON работает без входа. При закрытии страницы несохранённые ответы теряются.

## Какой стиль предлагаем

За техническую основу взят профиль `android_studio` движка **ktlint 1.8.0**. Название профиля не означает автоматическое совпадение с любым встроенным форматтером Android Studio. Для воспроизводимости нужны одинаковый engine, конфиг и JAR дополнительных правил.

| Что оформляем | Первое предложение | Где выбираем альтернативу |
|---|---|---|
| Отступы | Четыре пробела | Комментарий к основе |
| Длина строки | 140 символов | F01: 120 / 140 / без жёсткого лимита |
| Последняя запятая в вызове | Сохраняем оба допустимых вида | F02 |
| Последняя запятая в объявлении | Сохраняем оба допустимых вида | F03 |
| Объявление функции | С четырёх параметров — столбиком | F04 |
| Конструктор класса | С четырёх параметров — столбиком | F05 |
| Аргументы вызова | Короткий вызов можно оставить в строку | F06: нужен ли перенос по числу аргументов |
| Уже многострочный вызов | Каждый аргумент отдельно, включая большие вызовы | Комментарий к основе |
| Пустые строки when | Пока оставляем автору | F07 |
| Короткий intent | Одно выражение без комментариев — в строку до 120 символов | F08 |
| Modifier | С двух распознанных вызовов — столбиком | F09: с двух / с трёх |
| Обычные цепочки | Короткая цепочка может остаться в строку | Комментарий к основе |
| Импорты | Группы java/javax/kotlin в конце, alias после них | Комментарий к основе |
| Двоеточия | `val name: String`, `class Sample : Base()` | Штатное правило пробелов |

140 — предложенный общий лимит, а не обещание автоматически разорвать любой литерал/комментарий. Перенос с четырёх параметров — оформление объявления; он не запрещает функции с большим числом параметров.

### Как это выглядит

Фрагмент фактического результата предлагаемого профиля:

```kotlin
data class CardOptions(
    val title: String,
    val count: Int,
    val enabled: Boolean,
    val subtitle: String
)
```

Цепочка Modifier переносится по вызовам, короткая обычная цепочка может остаться компактной. Полные примеры — [до](examples/before/Example.kt) и [после](examples/after/Example.kt). Все примеры в публичном репозитории учебные; исходников приложений здесь нет.

## Что добавляют наши пять правил

| Правило | В предлагаемом профиле | Назначение |
|---|---|---|
| `nur:modifier-chain` | Включено | Переносит известные синтаксические Modifier-цепочки с двух вызовов |
| `nur:type-colon-spacing` | Выключено | Позволяет сохранять оба вида пробелов при наследовании; пока используем штатный colon-spacing |
| `nur:nested-lambda-wrapping` | Включено | Сохраняет компактную вложенную trailing lambda |
| `nur:call-arguments` | Выключено | При включении переносит вызов с заданного числа аргументов |
| `nur:compact-intent` | Включено | Собирает подходящий короткий intent в строку |

Это дополнения к встроенным правилам ktlint, а не все правила инструмента. Алгоритмы и ограничения подробно описаны в [отдельном документе](docs/custom-rules.md). Числа 2/4/120 можно менять через `.editorconfig`; изменение алгоритма требует новой версии JAR.

**Известная зависимость:** строгие trailing-comma правила ktlint требуют `standard:wrapping`. Текущая замена `nur:nested-lambda-wrapping` не удовлетворяет зависимости по rule ID. В вариантах строгих запятых включён штатный wrapping и отключена замена; дополнительный перенос виден прямо в анкете. Предлагаемый профиль сохраняет оба вида запятых и эту несовместимую комбинацию не включает.

## Что лежит в репозитории

| Каталог | Содержимое |
|---|---|
| `config` | Точный предлагаемый `.editorconfig` |
| `survey` | Анкета на учебных примерах и выгрузка ответов в JSON |
| `examples` | Целый учебный файл до и после |
| `docs` | Соглашения, дополнительные правила, порядок решений и результаты проверок |
| `tooling/nur-ktlint-rules` | Исходники пяти правил оформления |
| `tooling/nur-quality-plugin` | Ранний прототип доставки конфигов и JAR через Gradle Sync |

Приложения, исходные корпоративные фрагменты, рабочие заметки и данные доступа сюда не включены. Это публичная площадка подготовки. Основная работа продолжается в `vikim-nur/android-code-style-lab`; предыдущую личную копию не используем как второй источник обновлений.

## Как собрать

Сборка использует **JDK 21**, выходной bytecode рассчитан на **Java 17**. Gradle Wrapper 9.4.1 и checksum дистрибутива закреплены; Kotlin для сборки — 2.2.21.

```sh
./gradlew :ktlint-rules:jar
```

JAR правил появится в `tooling/nur-ktlint-rules/build/libs/`. Прототип доставки собирается отдельно:

```sh
./gradlew -p tooling/nur-quality-plugin build
```

Первая сборка скачивает Gradle и зависимости. Её время нельзя использовать как оценку обычной проверки небольшого Android-проекта.

## Как планируем использовать в Studio, хуке и CI

- **Studio:** IDE-плагин ktlint с согласованным engine и проектным конфигом/JAR. В эксперименте проверены IDE-плагин 0.31.0 и engine 1.8.0; произвольные версии Studio/плагина не считаются автоматически совместимыми.
- **Перед коммитом:** форматирование выбранных файлов через будущий согласованный хук. Режим staged-файлов, частично staged изменения и допустимую задержку ещё нужно проверить.
- **CI:** проверка оформления без изменения исходников. После утверждения профиля подтвердим одинаковый результат с IDE и хуком.
- **Общий Gradle-плагин:** доставляет зафиксированные версии, конфиги и JAR; обычный Sync готовит управляемые файлы. Это прототип, не выполненное подключение приложений.

В предлагаемом профиле в `config` уже включены новые рекомендации. В ресурсах транспортного прототипа пока прежний тестовый профиль. Их не подменяем незаметно: сначала выбираем правила, затем переносим утверждённый профиль и повторяем технические проверки.

## Что проверено и что впереди

- 22 варианта анкеты и один целый учебный пример прошли настоящий ktlint: format → повторный format без изменений → чистый check.
- JAR пяти правил собран отдельно; его provider, Java 17 bytecode и результат на целом примере проверены.
- Сборка прототипа доставки и `validatePlugins` прошли.
- Сохранение/восстановление ответов и отказ импорта другой версии формы проверены.
- Фикстуры не доказывают компиляцию Android-приложения или одинаковую скорость на всех проектах.
- Итоговый принятый командой профиль ещё предстоит проверить в настоящей Studio, хуке, CI и отдельно разрешённом пилоте.

Результаты: [примеры](docs/example-verification.json), [сборки](docs/build-verification.json). Ответы команды и утверждение лидом пока ожидаются. Пустой ответ не считается согласием.

После обсуждения фиксируем решение и исключения по каждому пункту, проверяем выбранную комбинацию, утверждаем версию и проводим отдельный пилот. [Порядок решений](docs/decisions.md) · [Будущий перенос в корпоративный Git](docs/migration.md).
